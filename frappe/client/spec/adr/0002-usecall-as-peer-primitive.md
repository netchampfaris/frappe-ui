# `useCall` as a peer primitive to `defineDoctype`

**Status**: accepted

## Context

The v3 SDK's main consumer surface is generated by `TSInterfaceGenerator`: for each DocType, an entry is emitted under `src/doctypes.ts` that exposes `getDoc`, `getList`, `newDoc`, `getCount`, `bulkDelete`, `bulkUpdate`, and any whitelisted doc-methods or controller-methods. This is a doctype-centred design: every primitive is reached through `MyDocType.something()`.

A survey of the apps under `frappe-bench/apps/` (gameplan, helpdesk, drive, crm, builder, insights, hrms, and others) measured how data fetching is *actually* shaped today:

| API | Approx. call sites | Doctype-shaped? |
|---|---:|---|
| `createResource` (free-form URL) | 659 | No |
| `useCall` (newer, free-form) | 155 | No |
| `createListResource` | 136 | Yes |
| `useList` | 73 | Yes |
| `createDocumentResource` | 70 | Yes |
| `useDoc` | 56 | Yes |

Two-thirds of all data-fetching call sites today are *not* shaped like a doctype operation. The URLs include cross-doctype aggregates (`drive.api.permissions.get_shared_with_list`), public unauthenticated endpoints (`insights.api.public.get_public_chart`), polymorphic dispatchers (`drive.api.files.call_controller_method`), system queries (`frappe.apps.get_apps`), and bulk operators (`helpdesk.api.knowledge_base.delete_articles`, `move_to_category`). Many of these *cannot* be naturally re-homed under a doctype controller — they are cross-cutting by nature.

The v3 spec, prior to this ADR, only mentioned `useCall` in passing — as if it were a footnote, not a primitive. That framing was inconsistent with the survey reality.

We considered three closures of the gap:

- **(A) First-class `useCall`.** A generic composable that mirrors the older `createResource` shape but is Vue-reactive and integrates with the new CacheAdapter. No doctype binding. Free-form URL, manual `transform`, reactive params.
- **(B) Codegen everything.** Extend `TSInterfaceGenerator` to discover every `@frappe.whitelist()` method app-wide (not just on DocType controllers) and emit a typed `AppMethods` namespace. No escape hatch needed in principle.
- **(C) Both.** Codegen what's statically discoverable; `useCall` as the escape hatch for everything else (third-party endpoints, dynamic URLs, conditional dispatch).

## Decision

Ship **`useCall` as a peer primitive in v1**. It lives at `frappe-ui/frappe/vue` next to `defineDoctype` and is exposed directly from `createClient`. It is not a child of any DocType.

**Shape:**

```ts
const handle = useCall<TResult>({
  url: string | Ref<string> | (() => string),
  method?: 'GET' | 'POST' | 'PUT' | 'PATCH' | 'DELETE',  // default 'GET'
  params?: MaybeRefOrGetter<Record<string, any>>
        | { [k: string]: MaybeRefOrGetter<any> },         // per-key OR whole-object reactive
  immediate?: boolean,                                     // default true; false = manual
  enabled?: MaybeRefOrGetter<boolean>,
  debounce?: number,
  cache?: string,                                          // optional kv-channel cache key
  transform?: (raw: any) => TResult,
  onSuccess?: (data: TResult) => void,
  onError?: (err: FrappeResponseError) => void,
})

handle.data        // TResult | null
handle.loading     // boolean
handle.error       // FrappeResponseError | null
handle.promise     // Promise<void>
handle.call(args?) // primary v3 verb (matches Operation.call())
handle.submit(args?) // alias — eases createResource migration
handle.reload()    // refetch with currently-bound params
handle.dispose()
```

`useCall` does NOT write its result into DocStore. Cross-instance sync for doc-shaped responses happens only via `response.docs[]` ([ADR-0001](./0001-doc-freshness-and-completeness.md)).

Typed code-generation for `@frappe.whitelist()` methods (option B) is deferred to v1.1 as an `AppMethods` namespace. It will be additive — `useCall` will remain the escape hatch.

## Rationale

- **Closing the 67% gap is a v1 ship-blocker, not a polish item.** Any app with non-trivial custom RPC (every surveyed app) cannot migrate to v3 without `useCall`. Without it, v3 is a non-starter for real codebases.
- **`useCall` is small.** ~100 lines including the reactive wrappers. The cost of getting it wrong is low; the cost of not shipping it is the entire migration story.
- **Option (B) alone is too rigid.** Static discovery of `@frappe.whitelist()` methods can find typed signatures, but the survey shows ~40% of custom endpoint usage is dynamic in some way — conditional URLs, runtime-chosen methods, third-party endpoints. There must be an escape hatch.
- **Option (C) is the long-term destination**, but it requires (A) anyway. Ship (A) first; layer typed `AppMethods` on top once the discovery story is solid.
- **`useCall` deliberately doesn't write to DocStore.** The store is the doctype-bound primitive's job. Letting `useCall` mutate it would either require shape-sniffing (fragile) or an `intoStore` flag (a footgun for developers migrating from createResource). The clean answer is server-side discipline: endpoints that want sync append to `response.docs[]`, which is harvested regardless of which client primitive made the call.

## Consequences

- **Migration of the 659 `createResource` call sites is mostly mechanical.** Rename + minor option renames. A codemod is plausible. Apps adopt v3 incrementally without rewriting their custom RPC layer.
- **`useCall` is the recommended migration target** for old `createResource` calls. The `.submit()` alias is retained specifically to ease that.
- **Doc-shaped `useCall` responses are siloed by default.** A custom endpoint that returns `[{ doctype: 'GP Task', ... }, ...]` does not populate DocStore. Apps that want sync either (a) ask the server to also `frappe.response.docs.append()` those docs, or (b) keep the data local to the call. There is no client-side magic.
- **Spec surface grows by one top-level section** in `api.md` and one row in the `vue.md` primitives table. No new core concept beyond what already existed for `getDoc`/`getList`.
- **A typed-codegen story is still needed.** Without v1.1's `AppMethods`, every `useCall<T>` requires the caller to specify `T` manually — type safety is opt-in. Acceptable for v1, but the gap remains visible.
